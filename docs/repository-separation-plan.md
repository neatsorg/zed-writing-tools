# Zed 関連リポジトリの分離と個人用ビルドの手順書

作成日: 2026-09-20

本書は調査結果と実施手順。現時点では既存履歴の巻き戻し、新規リポジトリの作成、
ビルド・実機への配置・GitHub への push は行っていない。

## 合意した方針

- 機能を通常の Zed 向けに独立公開できる状態を保つ。
- 日本語化に関係しない機能を zed-i18n の変換処理・ソースへ移植しない。
- 未保存文書の機能は新設する `zed-scratch-buffers` で管理する。
- 組み合わせを管理する `zed-personal-build` を新設する。
  GitHub に置く場合も必ず private とし、公開する機能の必須依存にはしない。
- 公開することと、アプリのビルド済み配布・拡張ストア登録は別工程とする。
- 現行の実機の動作を保ったまま分離し、代替ビルドを検証してから置き換える。

| リポジトリ | 正本と責務 | 公開方針 |
| --- | --- | --- |
| zed-i18n の自分のフォーク | 翻訳・日本語化に関係する変更。元作者向け PR は専用ブランチ | 元作者のプロジェクトの派生として公開 |
| zed-writing-tools | 変換・校正・DeepL の3拡張と共通サーバー | 独立公開 |
| zed-word-counter | 通常の Zed 向け字数カウントのパッチとテスト | 独立公開 |

各公開機能から個人用ビルドへの依存は作らない。LSP 拡張はアプリと別に導入する。
本体パッチの外部利用者は通常の Zed ソースからビルドする必要があるが、日本語化版は不要。

## 実施手順

### 1. 現状の保全

1. 各リポジトリの HEAD、差分、remote、Zed の対象コミットを再記録する。
2. i18n の現行 HEAD を名前付きの退避ブランチまたはタグで保持する。
   追跡対象外の重要ファイルも調査し、既存の `.cache/zed` は消さない。
3. 実機の稼働中バイナリ、ランチャー、設定、拡張の配置とバージョンを記録する。
   バイナリ差し替え前に戻せるコピーを用意する。秘密を含みうる設定はリポジトリへコミットしない。
4. i18n の remote を fetch し、アクセスキー PR の取り込み状況と3コミットの公開状況を再確認する。

実機の調査結果（2026-09-20、ステップ1レビューで実機と照合）:

- 対象アプリはユーザー環境に配置した統合ビルド。
  Preview版とは別の配置である（版・稼働状況は環境ごとに確認する）。
- `dev.zed.Zed.desktop` と `dev.zed-i18n.Zed.desktop` は対象アプリを直接参照する。
  `dev.zed.Zed-Preview.desktop` は Preview を参照する。
- 3拡張の配布物は Zed の開発用拡張作業ディレクトリにあり、各 `0.1.0` のみ。
- `settings.json` 関連ファイルは現行と複数世代のバックアップを確認した。具体的な配置先や世代数は公開資料に記録しない。

設定バックアップはアプリのロールバック用コピーを兼ねない。次の作業では、現行アプリ一式を
別名で保全し、ランチャーと拡張の実体も記録する。上記は配置の確認であり、退避完了を意味しない。

### 2. 個人用ビルドの管理先を用意

`zed-personal-build` を独立 Git リポジトリとして新設する。最低限の構成案:

```text
README.md
sources.lock.toml
scripts/prepare
scripts/check
scripts/build
scripts/deploy-local
compat/                  # 組み合わせにだけ必要な調整差分
docs/verification.md
.gitignore
```

固定情報には Zed・i18n・各パッチのコミット、パッチファイル、適用順、必要ならハッシュを記録する。
開発中はローカルパスから取得できるようにするが、隣接ディレクトリや未コミット変更を
暗黙に読み込まない。公開後も浮動する HEAD や latest に依存しない。
取得したソース・ビルド成果物・設定バックアップ・認証情報は Git 管理から除外する。

### 3. i18n から字数カウントの移植を除いた候補を作る

まず別ブランチ・別チェックアウトで分離後の候補を作り、現行ビルド環境は残す。
戻す対象は上記3コミットに限定し、アクセスキー修正が保持されていることを差分で確認する。

fetch 結果により未公開の分岐を採用する。現行 `263c50c` を退避した後、
アクセスキー修正とドキュメントが取り込まれた `b532fec` から新しい継続ブランチを作る。
そこへ字数カウント3コミットは cherry-pick しない。上流には3コミットがないため、
上流向け revert を作る必要もない。

確認では `736cd43..263c50c` の字数カウント差分と、`736cd43..b532fec` の上流取り込み差分を
区別する。現行 HEAD との単純な差分をすべて削除対象として扱わない。
旧ブランチは退避として残し、reset や force-push は不要。
適用済みのキャッシュへ逆パッチを重ねず、新しい作業用ソースを使う。

### 4. 独立パッチの取り込みへ切り替える

まず通常の Zed に字数カウントの正本パッチを適用して、単独で成立することを確認する。
次に、字数カウントの移植を除いた i18n 処理を完了させた生成先へ、正本パッチを適用する経路を検証する。

重要: i18n は抽出時の byte span を利用するので、未調整の機能パッチを先に当ててから
既存 manifest を使用してはいけない。基本候補は「元ソース → i18n → 独立機能パッチ」。
これは適用成功を確認済みの順序ではなく、次の工程で検証する案である。

- 最初に `git apply --check` で競合を確認する。
- 翻訳による行変更がパッチの前提と衝突する場合は、個人用ビルドの `compat/` に組み合わせ専用の
  小さな調整を置く。必要なら固定した共通祖先を使った3-way適用を検討する。
- 機能全体を Python や別の Rust ファイルへ手作業で複製する方式には戻さない。
- 新機能の翻訳接続も統合側で管理する。通常版の機能パッチは英語で成立させる。
- i18n の入力リポジトリは clean のまま、変更されるのは個人用ビルドの作業用 Zed ソースだけにする。
- 再実行時に二重適用・古い生成物の混入を起こさず、不一致なら停止する。

ここで分離前と同等の字数カウントが動くことを確認できたら、i18n の通常作業ブランチを
字数カウント移植のない状態に整理し、両リポジトリの説明を更新する。
生成済み Rust ソースを直接直すことは開発作業として許容するが、成果物は必ず正本パッチへ戻す。

### 5. 未保存文書の独立リポジトリを新設

`zed-scratch-buffers` を次の構成で新設する。初期の対象 Zed は、統合対象と同じ v1.20.2 の
コミットに固定する。機能は既定オフとし、通常の Zed 単体で有効化できるようにする。

```text
README.md
upstream.toml
patches/
scripts/prepare
scripts/check
docs/design.md
docs/verification.md
```

実装の要件:

- 表示は `Untitled-1` / 日本語化時は「無題-1」。タブ名に `.txt` は出さない。
- 内部ファイルは永続データ領域の `.txt` とし、実際のバッファに紐づけて LSP を利用する。
- 初期言語を Plain Text に固定する。
- 内部の固有 ID と表示番号を分け、番号再利用で旧文書を上書きしない。
- 通常の保存で正式保存先を尋ねる。成功時だけ通常ファイルへ移行し、キャンセル時は下書きを保つ。
- 個別タブを閉じた場合は保管して番号を解放し、アプリ終了の場合は再表示する対象として保持する。
- 既存の Hot Exit を活かす。閉じた下書きの復元一覧は通常終了時の復元とは分けて実装する。
- 字数カウントや writing-tools を必須依存にしない。LSP 接続は通常の Zed の仕組みを使う。

実装前に確定する詳細は、番号の範囲（ウィンドウ単位か全体か）、保管期限、
分割ペインで最後の表示を閉じた際の扱い。ユーザーの合意済み要件は
[未保存文書調査](scratch-buffer-research.md)も参照する。

### 6. 単独・組み合わせの検証

少なくとも以下の組み合わせを検証する。全組み合わせのフルビルドを毎回要求するのではなく、
変更に対応する型検査・対象テストと、実際に配布する組み合わせのビルドを行う。

| 組み合わせ | 主な確認 |
| --- | --- |
| 通常の Zed ＋字数カウント | 単独適用、既定オフ、設定切替、集計 |
| 通常の Zed ＋未保存文書 | 単独適用、固定名、保存・番号再利用・復元 |
| i18n ＋両パッチ | 適用順・翻訳・アクセスキー・両機能の共存 |
| 上記 ＋ writing-tools | 内部 `.txt` で校正・変換・翻訳が動作 |

下書きは保存データを扱うため、書き込み失敗、保存ダイアログのキャンセル、同時作成、
同じ文書の分割表示、終了・再起動、番号衝突をテストする。
異常終了では永続化済みの最新内容を復元できることを確認し、最後の未書き込み分まで無条件に保証しない。
DeepL の実送信を伴う検証は明示的な操作で行い、自動テストではダミーを使用する。

### 7. 実機への導入

1. 個人用ビルドで、固定した組み合わせのアプリを生成する。
2. 稼働中アプリと別の配置先に置き、まず別のテスト用ユーザーデータで起動確認する。
   利用する版の CLI のユーザーデータ切替方法を確認し、既存セッション DB を実験で破壊しない。
3. 設定構文・起動・日本語表示・アクセスキー・字数・下書き・LSP を確認する。
4. ユーザーの編集中文書を確認してから通常終了し、ランチャーまたは配置先を切り替える。
   稼働中の Zed を強制終了しない。
5. 通常の設定・既存の3拡張で動作を確認する。問題があれば保全した旧バイナリへ戻す。
6. 本体の自動更新で独自パッチが消えないよう、更新元・自動更新設定を確認する。
   設定変更が必要な場合はその効果を明示する。ビルド記録には使用コミットと成果物のハッシュを残す。

### 8. 公開準備

- 各公開機能に単独の導入手順、対象 Zed、ライセンス・必要な通知、検証範囲を記載する。
- Zed 本家へ提出する場合は、本家フォークの機能ブランチへパッチを適用する。
  パッチリポジトリを正本とし、二箇所で別々に機能開発しない。
- LSP のサーバー配布と拡張登録は本体パッチの公開と切り離す。
- 相対リンク `../zed-i18n` 等は公開後の正しい GitHub URL に直す。
- `zed-personal-build` は push 前に private であることを確認する。
  private であっても秘密やユーザー文書をコミットしない。
- 今回の手順書作成は push・PR・リポジトリ公開の実施には含めない。

## 分離完了の判定

1. i18n のツールソースに字数カウント・下書き管理の実装が含まれていない。
2. 各機能は通常の Zed の固定コミットへ単独で適用・検証できる。
3. 個人用ビルドが正本の固定リビジョンから全部入りアプリを再現できる。
4. 翻訳・統合の調整だけが個人用ビルド側にあり、機能全体の二重管理がない。
5. 実機で元の機能を維持し、旧版へ戻せる。
