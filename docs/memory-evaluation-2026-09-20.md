対象: 現在の zed-writing-tools とインストール済み依存。実装・設定・実機への配置は変更していない。

## 測定条件

ローカル Node.js v26.8.2、Linux。各ケースを別プロセスで起動し、測定前に明示 GC とイベントループ待機を3回実施。PSS は /proc/self/smaps_rollup、ヒープ等は process.memoryUsage()。単回の原因切り分け実験であり、実機の定常値・上限値ではない。RSS/PSS にはアロケータが保持する未使用領域も含まれる。arrayBuffers は external の内数なので加算しない。

短文: 「これは日本語の文章です。しかし、しかし、食べれるものを確認します。」

| 実行ルール | PSS MiB | heapUsed MiB | ArrayBuffer MiB |
| --- | ---: | ---: | ---: |
| 非形態素解析5ルール | 60.0 | 8.3 | 0.2 |
| no-dropping-the-ra のみ | 332.7 | 79.3 | 89.8 |
| 全12ルール | 334.0 | 79.6 | 89.8 |

非形態素解析5ルールは sentence-length / no-nfd / no-invalid-control-character / no-zero-width-spaces / no-kangxi-radicals。残る7ルールは直接または analyze-desumasu-dearu 経由で kuromojin を使う。

## 結論とコード上の根拠

1. **支配的なのは辞書・解析器の固定費。** src/engines/proofread.js は全プリセットを import するが、import だけならPSS約59〜60 MiB。kuromojin は最初の解析要求で辞書をロードし、モジュール内の _tokenizer と解決済み Promise が保持する。同一プロセスのルール間では共有されるが、別サーバープロセス間ではJSオブジェクトや展開済みバッファを共有しない。機能数に比例したメモリ削減は期待できない。
2. **キャッシュは件数制限のみ。** node_modules/kuromojin/lib/kuromojin.js の LRUMap(10000) は入力文字列とトークン配列を保持する。入力長・トークン総数・バイト数の制限はなく、文書を閉じた際にもこのキャッシュを消す処理はない。無制限件数のリークではないが、長い入力の履歴を多数保持できる。
3. **3万字の制限はCPU対策。** src/engines/proofread.js の HEAVY_RULES は5ルールを外すが、残る no-dropping-the-ra / no-double-negative-ja / no-mix-dearu-desumasu が辞書を使うため、辞書メモリは減らない。
4. **キャンセルは結果破棄であり、解析中断ではない。** src/lsp/diagnostics.js は200msのデバウンスと古い結果の破棄を行う。proofread() は受け取った signal を使わず lintText() を実行する。イベントループを占有する解析の中断は、signalチェック追加だけでは実現しない。ワーカー化は応答性対策になり得るが、辞書複製による増加を避ける設計が必要。
5. **変換・翻訳の分離は有効。** 各 features エントリーは校正エンジンを import しない。実機の以前の観測では各プロセスPSS約23〜27 MiBだった。3サーバー統合による節約はあり得るが、校正の固定費とは規模が異なり、独立配布や応答性とのトレードオフがある。
6. **ルール構成キャッシュは優先度が低い。** kernelOptionsByRuleNamesKey は Map だが、現LSPは初期化時に無効ルールを固定するため、通常は文字数閾値の前後で最大2構成。文書履歴キャッシュと混同しない。

## キャッシュの分離実験

kuromojin を直接使い、番号だけ異なる約50字の入力を2000種類解析。別プロセスで通常キャッシュと noCacheTokenize:true を比較。

| ケース | 辞書ロード後 heapUsed | 2000入力後 heapUsed | 2000入力後 PSS |
| --- | ---: | ---: | ---: |
| 通常キャッシュ | 76.7 MiB | 87.4 MiB | 393.2 MiB |
| キャッシュなし | 76.7 MiB | 76.8 MiB | 383.3 MiB |

この入力ではキャッシュによる保持ヒープの差が約10.6 MiB。実際の長文編集や上限10000件での増加量は未測定で、単純な外挿はしない。キャッシュなしでも辞書は残る。キャッシュはルール間・再検査の解析再利用に効くため、全面無効化のCPUコストは別途検証が必要。

## 辞書の構造

配布された gzip を展開したサイズは、tid_pos 40 MiB、tid 10 MiB、unk 10 MiB、unk_pos 10 MiB、base/check 各8 MiB、接続コスト約3.3 MiBなど。保持された ArrayBuffer 合計は約89.8 MiB。さらに target_map はJSオブジェクトと配列に展開される。ファイルが10/40 MiB単位であることだけで余剰領域と断定はできず、辞書レコード参照範囲を確認せず末尾ゼロを削るのは不適切。

NodeDictionaryLoader は展開済みBufferを Uint8Array にコピーし、DictionaryLoader は複数辞書を並行ロードする。初期ロード中の一時メモリ増加要因になるが、今回ピークは測定していない。

## 改善の順序

- まず解析結果キャッシュに入力長・トークン数または推定バイト量の予算を設ける案を検証する。単回検査内の再利用を残し、古い大きな入力の保持を制限する。診断一致と連続編集時CPUを確認する。
- 次に複数校正サーバーが必要になる単位と寿命を特定する。辞書を持つプロセスが増える負担は大きい。共有解析サービスは将来案であり、設定・文書・障害の分離と接続管理が必要になる。
- 固定費を本格的に下げるなら辞書の表現・ロード方式を検証する。レコード意味を保ったバッファ縮小や target_map の圧縮表現は候補だが、削減可能量は未実証。形態素解析器の置換はトークン分割、品詞、UTF-16位置、校正結果の互換性を伴う大きな変更。
- 応答性は最新ジョブ優先の実行制御とワーカー化を別途評価。ワーカーを増やすだけでは省メモリにならない。
